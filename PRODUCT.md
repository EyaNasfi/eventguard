# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Stack

React + Vite + TypeScript, Tailwind CSS. The frontend talks to the FastAPI backend (the EventGuard gateway and EventSim). The backend already exists in this repo; the frontend does not exist yet.

## Users

1. **Event operations staff** (simulated reader / editor / admin personas). They are not technical. They use a chat to get a routine job done quickly and safely, mostly duplicating an event edition (N → N+1) or archiving old ones. They approve or reject the writes the agent proposes.
2. **PFE jury and supervisors** watching a 5-minute live demo. They need to see three things in order: a normal task succeeds, an attack works on C0, and the same attack is blocked on C3 with its trace in the audit log.
3. **Aya (researcher)** running experiments. She compares configurations C0–C4 on the attack bench while iterating on the security layers.

## Product Purpose

EventGuard is a secured AI assistant for operating an event platform. It is an end-of-studies (PFE) research project at Républik Group, which runs B2B events. Staff ask in a chat for operations. The agent plans the steps and calls tools over MCP. Every tool call goes through a security gateway.

Success has two sides:
- **Operations:** staff finish a duplication or archive task correctly, with every write shown in a preview and approved by a person before it runs.
- **Research:** the evaluation shows, with confidence intervals, how each protection layer lowers attack success without hurting task success.

## Positioning

The agent never acts directly. Every tool call passes through a gateway that enforces:
- role-based rights
- archive, never delete
- write quotas
- filtered outputs
- tool results treated as untrusted data
- a hash-chained audit log

Every write shows a preview and needs a signed, single-use human approval. The protections are measured, not just claimed: an attack bench runs against five configurations, from C0 (no protection) to C4 (all protections plus an injection detector).

## Operating Context

- **Surfaces planned:**
  - agent chat with write previews and approvals
  - evaluation dashboard (C0–C4 results)
  - EventSim admin UI (browse and edit editions, events, sessions, speakers, partners and attendees, according to role)
- **Live demo ritual (about 5 minutes):** a normal task, then an attack on C0 that succeeds, then the same attack on C3 that is blocked, then the trace in the audit log. Switching configuration and finding the audit entry must be quick and easy to read on a projector.
- **Attack bench:** 80–100 attacks in 8 families, for example indirect prompt injection hidden in event descriptions or speaker bios.
- **Metrics:** attack success rate, task success, false refusals and approvals per task, each with a confidence interval, per configuration.
- **Roles (ADR-002 rev. 1):**
  - reader: reads everything except attendees and internal notes
  - editor: writes only in draft editions, can archive events one at a time, can send notifications
  - admin: everything, including the outbox and config
- **Notifications:** go to an outbox. They are never really sent.

## Capabilities and Constraints

- **No delete anywhere:** archive and unarchive only. Archiving is not cascading, so each write is explicit and visible in the state diff.
- **Draft edition:** the target edition (e.g. 2027) is created as `draft`. Editors may write only into draft editions.
- **Status values:** editions and events are `draft | active | archived`.
- **Test endpoints:** `/_test/*` (reset, snapshot, state diff, outbox, canaries) is for the harness only. It uses a separate secret and must never appear in operator-facing UI.
- **Canaries:** confidential fields (attendee contacts, private notes, the system prompt) carry canary markers so leaks can be detected.
- **Seed 42 reference:** editions 2025 (active), 2026 (active) and 2027 (draft, empty), with 22 events. Duplicating 2026 → 2027 creates 10 events.
- **Agent model:** Gemini, via n8n. The served model version must be logged on every run.
- **Undecided:**
  - how the frontend authenticates and maps to a role
  - whether the dashboard reads live harness runs or exported result files
  - whether the three surfaces are one app or several

## Brand Commitments

These are binding visual constraints from the user:
- Dark operations console: dense but calm and readable, precise, trustworthy.
- Color only for meaning: status, risk, blocked vs allowed, approval needed.
- No decorative gradients, no glassmorphism, no generic AI-SaaS look.
- Status is never shown by color alone: always a word or icon too.

## Product Principles

1. **Nothing writes without a person seeing it first.** Every write is shown as a preview and confirmed by a signed approval, and the interface makes that step unmistakable.
2. **Show the guard at work.** Allowed, blocked and pending decisions, with their reasons and audit trail, are first-class information, not hidden logs.
3. **Untrusted content stays visibly untrusted.** Text that comes from records or tool results is shown as data, never as instructions or interface.
4. **Measured, not claimed.** Results always show configuration, sample size and confidence interval.
5. **Fast for the non-expert.** A routine duplication takes as few steps as safety allows, in plain operational language.

## Accessibility & Inclusion

- WCAG 2.2 AA contrast.
- Strong, visible focus states. Fully usable with the keyboard, including approving and rejecting writes.
- Status, risk and allowed/blocked states are never shown by color alone.
- Must stay readable on a projector during the jury demo.
